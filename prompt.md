# Стартовое задание на разработку Orkestr EMP

Ты работаешь над единым Windows-приложением Orkestr EMP для инвентаризации
компьютеров и управляемой установки/обновления ПО. Рабочая папка — `Orkestr EMP`.
Здесь проектные документы, HTML-макеты и M1: Rust domain/storage/application/console/CLI.
Перенос разработки и сборка: `docs/development.md`. Legacy study copies и приватные
pilot outputs вынесены из репозитория; не считать их зависимостями workspace.
Добавлен M3.1 offline `inventory`: manual/CSV preview/apply, typed provider reports,
software normalization, SQLite v4. Сначала прочитай `docs/m3-inventory-core.md` и
`docs/m3-inventory-verification.md`: не создавай эти модели/импорт повторно.
M3.2 подключил manual/CSV к консоли/API (Admin), safe last/head provider status (Viewer+),
SQLite v5 durable apply receipts. Читай `docs/m3-console-api.md` и
`docs/m3-console-api-verification.md`. Не повторяй wiring и не выдавай это за AD/CIM scans.
Есть локальная egui-консоль и M2 dev-контур HTTPS/RBAC/DPAPI/remote UI, но нет
production-приёмки SCM/domain/PKI. M3.4–M3.6 уже добавили сетевой Inventory,
управляемые MSI/EXE, одобрение и сверку. Серверные M3–M5 теперь добавляют все штатные
шаги Deploy, библиотеку и политики; SQLite v10. Читай `docs/m3-m5-server.md` и
`docs/m3-m5-verification.md`, не создавай эти механизмы повторно. Текущий PC01
состоит в example.test; владелец разрешил пилоты на этом ПК и SERVER01. Не менять домен/сеть.
Ассистент прошёл source/download/trust, но quiet install отклонён. Повторять
исследовательские vendor установки нельзя; очистка оставшегося каталога на SERVER01
ожидает явного решения после automatic approval rejection, см. протокол.
Прочитай `docs/m1-core.md`, `docs/m1-console.md`, `docs/m1-console-verification.md`;
не создавай ядро и UI заново. Следующий этап — только по текущему запросу владельца.
Для M2 также прочитай `docs/m2-server.md`, `docs/m2-verification.md`.

Приоритет владельца от 2026-11-26: сначала завершать серверные M3–M5.
Дизайн текущей консоли требует пересмотра. Перед выпуском добавлен M5.5:
оценить веб-интерфейс без отдельного Rust-клиента, установку только сервера,
затем веб-дизайн и обращения к API. Это предпочтительное направление для оценки,
а не окончательный выбор UI. Не развивать оформление egui вместо серверных этапов.

## Подтверждённые ограничения

1. Современный спокойный Windows UI; темы Light/Dark/System.
2. Один сервер, несколько консолей. Сервер продолжает задачи без UI.
3. **V1 без постоянного агента**, WinRM/CIM; не называй endpoints агентами.
4. Развёртывание с одобрением по умолчанию, возможность явной автополитики.
5. Настраиваемые источники версии JSON API / HTML selector / regex и download URLs.
6. Auto-download и auto-deploy — разные разрешения, не включаются одно за другое.
7. Server cache и единые quotas/waves/retry, чтобы не запускать всех одновременно.
8. Подключение ПК отдельным окном; credential profile — другим окном.
9. DPAPI CurrentUser под identity службы на этом сервере, без требования переносимости.
   Смена машины/identity требует повторного ввода; не обещай «пароли невозможно потерять».
10. Никаких обходов TLS, NTLM/UAC политик и автоматических правок firewall при запуске.
11. Выбран макет A, сохранить понравившийся владельцу геометрический знак Orkestr.
12. Open-source продукт для небольших/средних организаций; начальная сеть владельца
    около 50 ПК, это не жёсткий лимит продукта. Лицензия нового продукта уточняется до релиза.
13. Обязательны статические/динамические коллекции с редактором И/ИЛИ, preview
    количества/списка ПК и установленного ПО. В UI «Группы», «Умные», «Ручные»;
   интерактивный HTML-пример есть в A, локальный Rust engine/редактор реализован в M1;
   production/domain приёмка и живая library reference ещё не закрыты.
14. Коллекции Chrome: установленная версия равна/ниже последней известной в библиотеке
    через динамическую ссылку, не зашитый номер; Unknown отдельно, approval не обходить.
15. RAM-фильтры: >=16, >=8, <8 и непересекающийся диапазон 8–<16 ГБ; numeric comparisons.
16. Вложенные папки и подгруппы: Приложения → Chrome → Последняя/Старая версия.
    Создание, перенос без циклов, union без повторов; не путать с логическими И/ИЛИ.
17. Сохранить подробные данные ПК из Inventory (F21). Не вырезать другие согласованные
    возможности из-за того, что макет показывает их кратко.

## Как выполнять

- M1, M2 dev-контур и серверные M3.1–M3.6 реализованы в описанных границах;
  M2 acceptance и реальный пилот M3 остаются открытыми. Продолжай незавершённые
  серверные пункты по актуальному roadmap. **Не перепрашивай число ПК и выбор A/B**:
  около 50 подтверждено; дизайн пересматривается в M5.5 по D14. Сеть/ОС/роли/пилотные приложения уточняй только когда
  они реально нужны текущему этапу; не блокируй создание ядра всей анкетой сразу.
- Предложи ограниченный план текущего milestone. Не пытайся реализовать весь roadmap
  одним монолитным файлом. Не начинай M1 заново; ориентируйся на текущий запрос и
  незакрытую приёмку в roadmap.
- Текущий стек сервера Rust + SQLite + HTTPS; egui — существующий интерфейс для
  проверки. Веб-вариант рассматривается в M5.5, не смешивай его разработку с текущими
  серверными этапами. Если предлагаешь сменить серверный стек, объясни перенос и зависимости.
- Сначала тестируемые модели/state machines и миграция на копиях, затем wiring UI/API.
- Коллекции не откладывать как необязательный косметический фильтр: engine/редактор
  и numeric/static preview — M1; живой эталон библиотеки подключается вместе с M4.
- HTTP handlers возвращают job_id, длительная работа живёт в bounded workers.
- Approval привязан к immutable package revision и artifact hash.
- После crash remote install может продолжаться: reconcile, не слепой повтор.
- Реальный byte limiter не заменяется полем Mbps поверх Copy-Item.
- Секреты не в argv/logs/exports/API reads. Никакого fake encryption в HTML/localStorage.
- Нет фиктивных результатов, seeds/fixtures явно учебные. Недоказанные тесты — Not run.
- Никаких установок, удалённых команд, reboot, service/firewall/domain изменений
  без явного разрешения и конкретных тестовых целей.

## Готовность одного этапа

Код компилируется, тесты этапа фактически выполнены, smoke проверен,
документы соответствуют поведению, известные ограничения и неподтверждённые проверки
перечислены. Обнови roadmap и журнал решений. В ответе перечисли сделанное,
команды/результаты тестов и оставшиеся риски. Не заявляй production readiness
только по успешной компиляции или по старым отчётам соседних проектов.
