# Безопасность и сохранение учётных данных

Это требования к реализации; HTML-макеты ничего не шифруют.
M2 реализует локальный dev-контур DPAPI/RBAC/HTTPS: [m2-server.md](m2-server.md).
SCM/domain/PKI lifecycle ещё не приняты; Rustls chain/name/expiry **не** означает
реализованную проверку CRL/OCSP. Требования ниже не объявляются целиком выполненными.

## Три разных типа входа

1. **Оператор → Orkestr server:** персональная авторизация консоли.
2. **Orkestr server → AD:** поиск OU/компьютеров, права чтения каталога.
3. **Orkestr server → целевой ПК:** сканирование/развёртывание.

Не смешивать их в одном поле «логин». AD read account не обязан быть endpoint admin.
Задания с явным credential profile не должны молча падать обратно на привилегированную
identity службы, если профиль не расшифровался. Это fail-closed.

## DPAPI на выбранном сервере

- Windows `CryptProtectData` / `CryptUnprotectData`, **CurrentUser scope** под
  постоянной учётной записью службы. LocalMachine по умолчанию не применять:
  привязка к машине сама по себе не изолирует секрет от других её пользователей.
- Сохранение через HTTPS только на сервере, а не шифрование на клиенте с отправкой
  чужого DPAPI ciphertext. Профиль службы должен существовать и быть доступным.
- Startup self-check под фактической identity службы: SID, профиль, DPAPI round-trip
  отдельного тестового значения; тест не изменяет реальные секреты.
- В metadata — UUID, имя профиля, login, разрешённые цели, SID владельца, timestamps.
  В job/SQLite export — только ссылка. Ciphertext не возвращать обычным API.
- Предпочтительно хранить DPAPI blob в отдельной таблице защищённой базы, metadata
  и blob записывать одной транзакцией; ограничить чтение таблицы repository-слоем.
- ACL каталога/backup: service SID/identity, SYSTEM и уполномоченные администраторы.
  Console users не получают прямой файловый доступ к серверной базе.
- Пароль не помещать в argv, URI, переменные глобального окружения, шаблоны,
  debug serialization, события/ошибки. Передавать адаптеру по защищённому stdin/pipe.
- Минимизировать время plaintext в памяти, zeroize буферы где реально возможно,
  исключить Debug/Clone секретов. Полную невозможность извлечения из памяти не обещать:
  процесс должен расшифровать секрет для аутентификации; PowerShell/.NET оставляют копии.

DPAPI защищает хранение, **не гарантирует отсутствие сбоев и не заменяет backup**.
Администратор ОС или захваченный процесс службы способен получить доступ к секретам.

## Поведение при рестарте и ошибках

| Событие | Требуемое поведение |
|---|---|
| Закрыли консоль | Служба продолжает работу, пароль в клиенте не требуется |
| Restart службы / Windows | Тот же сервер + identity + целый профиль: расшифровка и продолжение очереди |
| Изменили identity службы | «Учётные данные недоступны: сохранены другой identity»; задачи заблокированы |
| Профиль удалён/DPAPI повреждён | Ошибка, без тихого сброса; повторный ввод в отдельном окне |
| Перенос на другой сервер | Новый ввод; переносимое восстановление не входит в scope |
| Истёк/изменился пароль в AD/ПК | Auth error → приостановка повторов профиля, запрос обновления |
| Повреждена БД | Не создавать пустую поверх старой; read-only диагностика и восстановление |

При смене service identity: остановить выдачу задач → завершить/сверить running →
backup → изменить службу → startup check → заново ввести секреты под новой identity
через сервер → read-only connection tests → разрешить очередь. Старые blobs не удалять
до подтверждения, но не обещать их расшифровку новой учётной записью.

## RBAC / аудит

Viewer: читать inventory/status без секретов и запуска команд.
Operator: запускать утверждённые пакеты по разрешённым целям.
Admin: менять источники, профили, права и политики.
Approver: если согласован — одобряет определённую revision и artifact hash.
Произвольный PowerShell и редактирование steps — право выполнения кода, не обычный просмотр.
Аудит обязателен для изменения источника, секрета (без значения), approval,
включения auto-deploy, изменения scopes/ролей, отмены и повторов.

## TLS / Windows remoting

Не отключать CA/CN/revocation policy ради успешного теста. Проверять hostname/IP SAN,
срок, цепочку и доверие на сервере, а не только на консоли. HTTP к собственному API запрещён.
Токены и ключи не писать в URL. Приватные ключи не выдавать через help/export.
Порты открываются администратором с узким scope; UI показывает необходимые изменения,
но не выполняет их неявно. Запрет NTLM — не обходить TrustedHosts или Basic.

## URL, HTML и цепочка поставки

- Только HTTPS по умолчанию; внутренний HTTP — отдельное небезопасное исключение,
  если вообще будет разрешено владельцем, не в baseline.
- Allowlist источников и доменов redirect; повторная проверка каждого redirect,
  DNS/IP, порта, лимит переходов. Защита от SSRF, DNS rebinding, loopback, link-local,
  metadata и внутренних сетей. Внутренний repository — явная allowlist host/CIDR,
  а не отключение SSRF целиком.
- Нельзя передавать Authorization/cookies на другой origin после redirect.
- HTML разбирать как текст/DOM в изоляции без JS; удалённое содержимое не инструкции.
- Проверять ожидаемые SHA-256/Authenticode publisher по политике. Hash, посчитанный
  после загрузки, даёт идентичность, но не доказывает доверенное происхождение.
- Reject path traversal, UNC/file://, опасные схемы, архивные zip-slip пути.
- Downloader не исполняет файл. Quarantine → verification → approval → deploy.
- Неподписанные внутренние пакеты допускаются лишь явной политикой + hash и одобрением.

## Backup

Согласованная SQLite backup + artifact manifest + защищённые blobs/config/TLS key.
Backup без DPAPI-профиля/ключей Windows не обещает восстановления паролей;
перенос на другую машину требует повторного ввода. Копии также секретны и требуют ACL.
Восстановление на том же сервере испытывается отдельно. Не копировать живой WAL вручную.
Шифрование диска BitLocker и защита системного backup — ответственность администратора.
