# Разбор двух программ

Дата: 2026-11-06. Исследованы независимые Rust-реализации в папках `app`,
не заявляется аудит всех бинарных файлов, встроенных toolchain и декомпиляций.
Пути ниже относительно `Craft Anything`. Исходники не запускались на удалённых ПК.

## Карта

| Область | Open Deploy | Open Inventory |
|---|---|---|
| Стек | `Cargo.toml:8–16`: eframe/egui 0.31.1, serde, chrono, roxmltree, rfd | `Cargo.toml:8–20`: тот же eframe, rusqlite, tiny_http, reqwest/rustls, rcgen, windows-service |
| Данные | `src/model.rs:235–302`: один JSON с пакетами, историей, настройками; backup перед сохранением | `src/storage.rs:7–19`: SQLite WAL, computers/log/sync_state/collections; содержимое объектов частично JSON |
| Централизация | `src/central.rs`: SMB-файлы запросов/ответов, снимок, heartbeat, эксклюзивный владелец | `src/server.rs`: HTTPS + общий bearer token, до четырёх обработчиков |
| Выполнение | `src/engine.rs`: PowerShell, WinRM, копирование в сессию, коды выхода, отмена | `src/windows.rs`, `scripts/scan.ps1`: CIM/DCOM или WinRM HTTPS, реестр ПО |
| AD | `src/ad.rs`: PowerShell ActiveDirectory, нужен модуль | `scripts/discover.ps1`: ADSI, подпись/шифрование, постраничный поиск без RSAT |
| UI | `src/main.rs`: большая монолитная консоль, редактор и диалоги | `src/ui.rs`, `src/ui/console_ui.rs`: консоль, карточка ПК и коллекции |
| Фон | `src/service.rs`, `src/setup.rs`: режим службы и central runtime | `src/main.rs`, `Install-Service.ps1`: отдельный сервер/служба |
| Секреты | `engine::Auth`: пароль только в памяти одного запуска | `windows.rs:136–172`: DPAPI-файл на хост, расшифровка исполняющим пользователем |

Полные корни: `pdqdeployconsole/app/` и `pdqinventoryconsole-2/app/`.

## Deploy: что сохранить

- `model.rs:51–126`: десять видов шагов и редактируемый пакет; install, command,
  PowerShell, file copy, sleep, message, reboot, logoff, nested package, scan.
- `engine.rs:137–165`: MSI/MSP/MSU, quiet/no-restart, коды успеха.
- `engine.rs:240–259`: разворачивание вложенных пакетов с пределом глубины.
- `engine.rs:261–338`: пул целей, события прогресса, тайм-ауты, глобальная конкуренция.
- `main.rs:2837+`: JSON/XML import; неподдерживаемые варианты отклоняются.
- `central.rs:73–87`: принцип optimistic concurrency при общих изменениях.
- `GUIDE_RU.md`: практические объяснения Local/Client/Server и WinRM.

## Deploy: чего недостаточно для нового продукта

1. Библиотека (`main.rs:1676–1750`) — восемь зашитых winget-рецептов.
   Нет настраиваемого обнаружения версии по API/HTML, артефактного хранилища,
   карантина, подтверждения релиза и server-side downloader. Winget на каждом ПК
   сам скачивает ПО: такой путь не обеспечивает требуемый контроль внешнего канала.
2. WinRM-сессия (`engine.rs:170–178`) не задаёт профиль `UseSSL`/порт/режим аутентификации.
   Нельзя просто подключить недоменную запись Inventory к этому движку.
3. `Auth` один на запуск. Нет сохранённых серверных профилей, их ссылок в retry
   и проверки, что учётная запись службы действительно может их расшифровать.
4. Ограничение количества целей не равно ограничению трафика. Нет site limits,
   раздельных слотов передачи/установки и устойчивых leases.
5. История и весь вывод в JSON растут вместе с конфигурацией; это не база очереди.
6. Отмена локального процесса не доказывает остановку удалённого установщика.
7. История после прерывания помечается Interrupted (`model.rs:280–289`),
   но повторный запуск без проверки состояния может повторить установку.
8. SMB writer обладает правом выполнения кода как сервер: это не многопользовательский RBAC.

## Inventory: что сохранить

- ADSI paging (1000), OU, исключения и disabled accounts (`discover.ps1`).
- GUID для переименований и сохранение старого скана при ошибке (`storage.rs:68–107`).
- Коллекции статические/динамические с AND/OR (`model.rs:125–207`).
- Безопасное чтение uninstall registry без `Win32_Product` (`scan.ps1:28–48`).
- Независимые провайдеры, предупреждения вместо выдуманных данных (`scan.ps1:61–95`).
- JSON в stdin вместо пароля в argv (`windows.rs:12–82`).
- Проверяемый HTTPS, пользовательский CA и hostname validation (`backend.rs:20–33`).
- DPAPI на стороне сервера, не на клиенте (`backend.rs:221–255`).
- Согласованный backup через `VACUUM INTO` (`storage.rs:160–170`).

## Inventory: что переделать или расширить

1. Общий bearer token предоставляет полный доступ, включая `/v1/shutdown`.
   Для нескольких администраторов нужны персональные идентичности, отзыв и роли.
2. `/v1/scan`, sync и command выполняют длительную работу внутри HTTP worker.
   Новое API должно возвращать ID задания, не держать HTTP 400 секунд.
3. Конфигурация bearer token находится в JSON (`model.rs:14–24`).
   В Orkestr клиентский token защищать локальным DPAPI, сервер хранит его hash.
4. Пароли AD явно не поддерживаются: ADSI использует текущую идентичность
   (`discover.ps1:12,28`). Отдельный доменный профиль — новое требование.
5. DPAPI-запись идёт через Set-Content без атомарной замены (`windows.rs:152`).
   Нужны транзакционное сохранение/версионирование, ACL, проверка identity и понятная ошибка.
6. Файл секрета привязан к hostname. После AD rename нельзя связывать секреты с именем файла;
   в Orkestr использовать стабильный UUID профиля и DeviceId.
7. SQLite хранит большую часть данных ПК одной JSON-строкой, нет нормализованного
   installed_software и сопоставления приложения с издателем/архитектурой/версией.
8. Сертификаты генерируются один раз, private CA key отбрасывается
   (`backend.rs:290–317`); понадобится явная процедура ротации без отключения TLS.
9. Сборка Linux-фич egui не означает поддержку Linux: Windows-only код и PowerShell.

## Вывод по объединению

Не переносить UI-монолиты через `include!` и не соединять два сервера.
Извлечь доменные модели и адаптеры, покрыть переносимые функции тестами,
выдать общий DeviceId, PackageRevisionId, CredentialProfileId и JobId.
Inventory берём как основу хранения/HTTPS/AD, Deploy — как основу шагов выполнения.
Сервер, очередь, профили подключений и библиотека — общие новые модули.

`investigation.cany`, toolchain, `target` и `dist` — не исходная база нового приложения.
