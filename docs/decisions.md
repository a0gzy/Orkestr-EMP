# Решения и открытые вопросы

## Подтверждено владельцем

- **D01:** современный спокойный интерфейс.
- **D02:** первая версия без агентов. Термин в UI — «компьютер» или «цель», не «агент».
- **D03:** один Windows-сервер, несколько административных подключений.
  Сейчас — нативные консоли; вариант работы через браузер рассматривается по D14.
- **D04:** развёртывание по одобрению по умолчанию, автополитика доступна явно.
- **D05:** секреты только на этом сервере; переносимое хранилище не требуется.
- **D06:** подключение компьютеров и ввод учётных данных — отдельные окна.
- **D07:** выбран **макет A**, боковая навигация и вкладки карточек; B остаётся
  только сравнительным материалом. Повторно выбирать A/B не нужно.
- **D08:** текущий геометрический знак Orkestr нравится владельцу — сохранить
  как визуальное направление, не заменять при реализации без согласования.
- **D09:** проект открытый, ориентирован на небольшие и средние организации.
  Первая конкретная сеть владельца — примерно **50 ПК**; это стартовый сценарий
  проверки, не максимальное число устройств и не обещание готовой масштабируемости.
- **D10:** обязательны статические и динамические коллекции: редактор условий,
  предпросмотр количества/списка подходящих ПК и установленного ПО. Динамические
  условия умеют сравнивать версию приложения с последней известной в библиотеке,
  а также числовые характеристики, включая RAM. Подробно: [collections.md](collections.md).
- **D11:** нужны вложенные подгруппы: `Приложения → Chrome → Последняя / Старая версия`.
  В макете есть папки, выборки и перенос; название в UI — «Группы компьютеров».
- **D12:** сохранять подробные данные ПК и остальные согласованные возможности
  исходных реализаций. Сокращённый HTML не является решением вырезать их из приложения.
- **D13 (M2, 2026-11-06):** текущий ПК разработки вне домена; домен есть и доступен
  отдельный доменный ПК для последующих согласованных тестов. Не присоединять текущий
  ПК к домену и не ослаблять TLS/TrustedHosts ради разработки.
- **D14 (2026-11-26):** сначала довести сервер по roadmap. Ближе к концу, до выпуска,
  отдельно разобрать замечания к дизайну и ошибки пользовательской проверки.
  Предпочтительное направление для оценки — веб-интерфейс без отдельного Rust-клиента,
  установка только серверной части. Это ещё не окончательный выбор технологии UI.
  Выбор макета A (D07) сохраняет историю направления, но не означает одобрения
  текущего дизайна реализации. Этап: M5.5 в [roadmap](../roadmap.md).
- **D15 (2026-11-26):** владелец поручил реализацию roadmap по M5 включительно
  и разрешил пилоты на текущем ПК и SERVER01. Первым реальным source выбран Ассистент:
  версия на официальной странице, загрузка из блока «Полная версия». Это не выбор
  тихих параметров установщика и не одобрение любого найденного vendor рецепта.
  Фактический PC01 на момент пилота состоит в example.test; D13 описывает прежнее
  состояние, присоединение к домену в этой работе не выполнялось.

## Предложения, не окончательные решения

| ID | Предложение | Причина |
|---|---|---|
| P01 | Rust-сервер; текущая egui-консоль для разработки, дальнейший UI по D14 | Сервер продолжаем независимо от будущего интерфейса |
| P02 | SQLite на локальном диске сервера + единый HTTPS API | Одна истина вместо JSON+SMB+SQLite |
| P03 | Принято как D07: макет A | Не делит единый продукт на две чужие консоли |
| P04 | Персональные client tokens с ролями в первой общей версии | Общий супер-токен не даёт аудит и отзыв |
| P05 | Автопроверка каждые 6 часов ± jitter; автозагрузка выключена до выбора | Разделить разрешения и не расходовать канал неожиданно |
| P06 | Глобально 2 передачи, 1 на площадку; jitter до 120 с | Осторожная отправная точка, не измеренная норма |
| P07 | CIM/WinRM HTTPS как желаемый основной путь | Сократить нужду в DCOM/Remote Registry; legacy оставить opt-in |
| P08 | Чистая серверная установка + импорт, не in-place update старых продуктов | Разные данные, протоколы, имена и identity |
| P09 | Тёмная / светлая / системная тема на каждой консоли | Персональная настройка без влияния на других |

## Что уточнить до реализации

1. **Масштаб:** старт — около 50 ПК, небольшие/средние организации. Позднее уточнить
   число администраторов, характер роста и одновременных заданий; это не блокирует M1.
2. **Сеть:** одна LAN или несколько VLAN/филиалов, VPN, пропускная способность,
   ограничения прокси/Интернета? На основании этого выбрать лимиты и интервалы.
3. **ОС:** минимальные Windows клиента/сервера, Windows Server Core, ARM64 нужны?
4. **Домены:** один лес или несколько, доверия, gMSA, NTLM разрешён ли политиками?
5. **Роли:** достаточно Admin/Operator/Viewer? Нужен ли отдельный Approver и
   запрет одобрять собственную правку пакета (four-eyes)?
6. **Каталог:** первые 5–10 приложений, официальные страницы/API, внутренние пакеты,
   требования к подписи и проверке SHA-256?
7. **Пилот:** какие ПК, сколько времени наблюдения, какие окна, допустимый процент ошибок?
8. **Пользователи ПК:** уведомление перед установкой, отсрочки, запрет прерывать работу,
   политика перезагрузки? Без агента интерактивные уведомления ограничены.
9. **Дистрибутив:** portable console или MSI, сертификат подписи, где публикуем обновления?
10. **Данные:** срок хранения подробных сканов, журналов, пакетов и персональных данных?
11. **Open source:** выбрать лицензию нового продукта и место публикации перед релизом;
    не смешивать с уже известными MIT-лицензиями исходных проектов.
12. **Языки:** русский основной; нужно ли сохранить английский в первом релизе?

Пока ответы не получены, это assumptions, а не скрыто принятые обязательства.
Для начала M1 информации достаточно. Остальные вопросы уточнять по мере необходимости
конкретного этапа, не превращать их все в предварительную блокирующую анкету.

## Журнал реализации — 2026-11-06, M1.1

Это технические решения текущего инкремента, не новые ответы владельца на открытые вопросы.

- Сохранён предлагаемый Rust/SQLite стек. Начато с `domain`, `storage`, `cli`;
  egui-консоль A подключается следующим инкрементом. Нет двух старых UI/серверов в одном процессе.
- RAM: байты установленной физической памяти = сумма `Win32_PhysicalMemory.Capacity`;
  отображаемая единица — GiB (2^30). Округлённый legacy `MemoryGB` не используется как
  точный installed RAM. Без полного набора модулей — Unknown.
- Условия используют трёхзначную логику. Preview закрепляет generation, timestamp,
  список ПК и их ПО одним снимком. В CLI freshness-порог пока явно фиксирован 24 часа;
  это диагностическое значение M1, не согласованная политика production-сканов.
- Сканирование не реализовано: тестовые complete snapshots — fixtures. Старый скан ПО
  HKLM считается Partial, поскольку не покрывает пользовательские установки; его
  строки видны, но не доказывают «не установлено»/соответствие software-фильтру.
- Ссылки на library versions моделируются и проверяются на fixture; нет сетевого
  discovery и production catalog matching до M4. Known и approved не смешиваются.
- Импорт требует явно выбранной локальной backup-копии, dry-run по умолчанию;
  apply транзакционный, проверяет hash и generation, CLI сначала делает новый backup.
  Неизвестные правила/шаги и identity conflicts блокируют весь импорт. Перенос
  legacy rounded-RAM rules без смены смысла пока не поддержан.
- Секреты/config/log/history/schedules не импортируются. Пакет — только неутверждённое
  определение для review; installer path не открывается. Полная миграция остаётся открытой.
- MIT notices сохранены отдельно; лицензия нового кода не выбиралась от имени владельца.

## Журнал реализации — 2026-11-06, завершение M1

- Добавлены `application` и `console` (egui 0.31.1). UI не открывает Store: один
  локальный worker, command/event queues по 8, non-blocking submit и явная backpressure.
  Это co-located backend, не Windows-служба и не будущий HTTPS client mode.
- Дизайн A сохранён: Workbench/Cobalt, тот же геометрический знак, side rail/status line.
  Локальные Segoe UI/Consolas с fallback; токены производны от `tokens.css`, HTML не изменён.
- Редактор поддерживает вложенные И/ИЛИ, manual members, RAM helpers и свободные
  numeric/text/software rules, parent selection/move и snapshot preview. Stale revisions
  возвращают конфликт, draft не теряется. Общая оценка счётчиков и preview закрепляет
  generation и timestamp, отдельный request token отбрасывает старые ответы.
- Темы/zoom персональны. База не открывается и не заполняется автоматически; для
  нового файла отдельный явный create. Локальный read refresh не запускает сканы.
- SQLite v2 additive migration: выключенный import review и package lineage;
  перед writable upgrade v1 создаётся согласованный non-overwriting backup.
- Уточнение поведения M1.1: unsupported legacy collection semantics теперь не блокируют
  весь реестр, а сохраняются read-only с явным warning/review_items. Это не активная
  группа. Identity conflicts/unresolved static members/unsupported steps блокируют импорт.
- Schedules/target lists/history metadata сохраняются только для review. Enabled всегда
  false, next/recurrence/was_enabled сохранены, targets сопоставлены с DeviceId либо
  показаны unresolved без создания ПК. Config/secrets/history outputs не переносятся.
- Явное «Происхождение» связывает PackageId между копиями одного Deploy-сервера;
  разные сервера не объединяются по совпавшему legacy ID. Каждая правка — новая revision.
- Сохранённые F21-разделы доступны в карточке/«Все данные». Реальные провайдеры/новые
  сканы остаются M3, mapping/discovery библиотеки — M4. Legacy HKLM coverage = Partial.
- Приёмка M1 локальная, fixtures явно синтетические. Настоящие данные владельца,
  release/security/license audit и полная Windows UI-матрица не выдаются за проверенные.

## Журнал реализации — 2026-11-06, M2 dev-контур

- Сохранены M1 engine/UI. Добавлены protocol/client/credentials/server, один HTTPS
  backend, SQLite v3 additive backup upgrade. Remote UI не читает серверные paths/SQLite.
- Персональные random 256-bit bearer tokens, только SHA-256 на сервере, expiry/revoke,
  Admin/Operator/Viewer. Это реализация P04 для dev-пилота, не утверждение, что весь
  production role scope/four-eyes согласован. Bootstrap локальный, DPAPI token на 7 дней.
- DPAPI CurrentUser под реальным process SID, persisted canary + round-trip + проверка
  всех blobs до listener. Без LocalMachine/fallback. NTFS-only, protected ACL и single
  instance handle. Никаких системных/сетевых изменений автоматически, кроме ACL явно
  выбранного **нового** data directory при init.
- Fixed read-only tests: AD LDAPS RootDSE или WinRM HTTPS CIM OS Caption. Отдельные
  credential kinds, exact-host scope. Password stdin JSON, no argv/global env/log output.
  AD discovery/scans/install/staging/HTTP compatibility/Kerberos-only остаются M3.
- Jobs: 2 workers/8 queue, durable idempotency, revision/authorization recheck, bounded
  safe-code audit/events; restart → Interrupted, не retry. Только queued cancellation.
- M2 snapshots до 8 MiB, не обещание production pagination/scale. Viewer/Operator не
  читают private legacy details/commands, Admin по-прежнему видит сохранённые F21 данные.
- SCM код и opt-in install helper написаны; установка/смена account/reboot/реальный
  домен/второй ПК не запускались. Rustls chain/name/expiry не выдан за CRL/OCSP hard-fail.
  M2 implementation и M2 acceptance разделены; следующий шаг — согласованный пилот.

## Журнал реализации — 2026-11-06, M3.1 offline-ядро

- Владелец выбрал **начать ядро M3**, не проводить сейчас доменную приёмку M2.
  Сетевые подключения, SCM/identity/firewall/domain изменения и установки не разрешались.
  M2 acceptance остаётся открытой; тесты localhost с собственными fixtures не заменяют пилот.
- Добавлен `inventory`, без сетевого/процессного runtime. Ручной/CSV discovery даёт
  preview добавлений/изменений/дубликатов/conflicts. Только DNS host/alias, не IP;
  metadata AD/старые сканы не стираются. CLI apply требует новый rollback backup.
- F21 имеет 23 typed providers. Missing/failed не становятся успешным пустым разделом;
  полный failure/unknown сохраняется отдельным report без обновления scan head/возраста.
  Partial не смешивает старые значения с новой датой; наблюдение датируется началом сбора.
- Software evidence сохраняет raw/normalized version, publisher, arch, scope/SID,
  product code/registry key; library ApplicationId/channel не угадываются до M4.
  HKLM-only остаётся Partial. Новый user adapter ещё не написан и полнота не заявлена.
- SQLite v4 additive migration + consistent pre-v4 backup для v1/v2/v3. M2 секреты/
  canary/jobs не переинтерпретируются. Старый v3 binary несовместим с v4;
  действующую службу автоматически не обновлять. Новые отчёты приватны, не public export.
- UI/API discovery/provider-status wiring, AD/CIM/WinRM adapters и весь deploy engine
  оставлены следующими инкрементами. Сокращений прежних функций/HTML-дизайна нет.

## Журнал реализации — 2026-11-06, M3.2 console/API wiring

- По «Продолжай» выполнен следующий объявленный инкремент: окно manual/CSV, remote
  API и статусы attempts/providers, без новых remote probes/сканов/установок.
- Добавление/правки Device registry в remote mode оставлены **Admin-only**; это
  ограничительный baseline, не скрытое расширение Operator. Viewer/Operator читают
  safe статусы, но не raw F21 evidence/user SIDs/Environment. Кнопки не заменяют RBAC.
- Файл выбирается/читается worker на компьютере консоли. Backend получает текст до
  24 KiB, не path; старый offline CLI сохранил 256 KiB limit. Legacy remote import не открыт.
- Preview на 5 минут, максимум 8/Store и 1/actor; новые drafts заменяют старые.
  Показаны previous/proposed name/site, alias target и generation. Apply подтверждён
  явно, с recheck под transaction и новым backend-generated backup при изменениях.
- SQLite v5 additive receipt: actor/preview ID → result. Devices/receipt/audit атомарны;
  replay после lost reply/restart не делает второй write/backup/audit. Неуспешные
  previews не durable, после restart нужны новый preview/confirmation, без автоповтора.
- Неоднозначный apply сохраняет ID в памяти окна для ручного retry. Закрытие окна
  не отменяет write; durable draft/recovery UI после закрытия процесса/смены actor нет.
- Safe Inventory status запрашивается on-demand, latest attempt отделён от current
  head. Legacy imports не получают выдуманного provider coverage. Все прежние F21 tabs
  сохранены; UI design A/знак/HTML не заменялись. Full native accessibility/DPI review впереди.
- M2 acceptance и сетевой M3/Deploy открыты; backup/receipt/history retention и большой
  registry load/SLO не приняты. M3.2 не объявляет network adapters готовыми.

## Журнал реализации — 2026-11-26, M3.6 и приоритет сервера

- По D14 добавлен M5.5 перед выпуском: пересмотр дизайна, оценка браузерного клиента,
  установка только сервера, затем работа выбранного интерфейса с API. Rust-сервер,
  SQLite, HTTPS и серверное исполнение продолжаются независимо от выбора UI.
- Следующим серверным инкрементом M3 добавлен EXE к существующим MSI-планам.
  EXE требует явную ограниченную тихую командную строку и системную GUID-запись
  с точным DisplayVersion. Параметры неизменяемы вместе с ревизией/hash; новый
  manifest не меняет прежние одобрения. Vendor-specific detection/success codes
  и остальные штатные шаги Deploy пока не реализованы.
- EXE запускается напрямую без shell; stdout/stderr дренируются без сохранения.
  Нужны Admin, отдельное одобрение и существующие WinRM HTTPS credentials.
  Неопределённый результат удерживает блокировку ПК до read-only сверки.
- SQLite v8 с backup до обновления v7. Старые MSI без execution остаются MSI;
  старый сервер новую схему не открывает. Регистрация EXE пока через API,
  консоль показывает параметры/ревизию/detection перед одобрением.
- Форматирование, Clippy, 113 тестов и сборка прошли. Реальный блок запуска
  проверен локальным безвредным EXE при подменённых WinRM transport/detection;
  подключений к компьютерам сети, установок ПО, изменений службы/сети и перезагрузок в этом
  инкременте не было. M2/M3 production acceptance остаётся открытой.
  [Контракт и проверки](m3-managed-installers.md).

## Журнал реализации — 2026-11-26–27, серверные M3–M5

- Реализованы все штатные workflow шаги, библиотека источников/загрузчик, known/approved
  references и политики с pilot/soak, окнами, quotas, durable retries/dispatch. SQLite v10
  с pre-upgrade backup. Новые возможности доступны через API; дизайн остаётся M5.5.
- ServerIdentity — отдельный явный Kerberos-профиль с DPAPI marker, без чтения пароля
  и скрытого fallback. Unattended требует opt-in и проверяемого неизменного рецепта;
  смена MSI ProductCode/источника/аргументов не наследует прежнее одобрение.
- Прошли 138 тестов, Clippy и сборка; на SERVER01 — synthetic EXE 0/3010 и policy pipeline,
  на SERVER01/PC01 — parallel/strict sequential transfers с payload pacing и Inventory.
  Неудачная попытка SystemScan не засчитана; исправлено сохранение Failed report и
  диагностики в workflow, повторный полный пилот прошёл. Тестовые каталоги очищены.
- Ассистент прошёл официальный source → download → Authenticode → Verified.
  Тихий installer не принят, новый vendor рецепт не опубликован. После неудачной
  custom action остался каталог на SERVER01; удаление отклонено automatic review
  (`blocked by policy`) и ждёт отдельного ответа владельца, обхода не было.
- Полная production/workgroup/SCM приёмка остаётся открытой. Текущий контракт:
  [m3-m5-server.md](m3-m5-server.md), результаты: [m3-m5-verification.md](m3-m5-verification.md).
