Справочник Orkestr EMP

Единое рабочее место для инвентаризации Windows-компьютеров, библиотеки ПО и управляемых обновлений. Две исходные программы уже существуют, но их объединение в Orkestr ещё не реализовано.

Что можно делать сейчас

Открыть HTML-макеты, сравнить навигацию, проверить учебные формы и выбрать направление. Нельзя устанавливать Orkestr-службу или подключать реальные ПК через HTML. Ни одна кнопка макета не делает этого.

Первое знакомство за несколько шагов

  1. Откройте макет A. Выберите TEST-PC-01 и вкладку «ПО» — оттуда можно перейти в библиотеку.
  2. В библиотеке выберите Atlas Editor, нажмите «Проверить пример». Результат извлекается из локального учебного ответа, без запроса к сайту.
  3. Откройте окно учётных данных. Прочитайте предупреждение DPAPI; настоящий пароль не нужен.
  4. Одобрите учебную версию и посмотрите «План развёртывания». Реальных задач нет.
  5. В «Политиках» измените число передач на площадку и сравните проекцию очереди.
  6. Переключите тему и откройте макет B — там те же сценарии организованы иначе.

Изменения макета находятся только в памяти. Перезагрузка сбрасывает их. Сохраняется только предпочтение темы.

Один сервер, несколько консолей

Согласованная схема: Windows-служба Orkestr управляет базой, заданиями, библиотекой и секретами. Консоли администраторов работают с ней по HTTPS. Целевые компьютеры обслуживаются без постоянного агента через WinRM/CIM.

План установки готовой версии

  1. Выбрать постоянный сервер, DNS-имя, защищённый data directory, service identity и правила доступа. Подтвердить поддерживаемую ОС после реализации.
  2. Установить подписанную/проверенную сборку и службу явным действием администратора. Конкретные команды появятся после создания установщика.
  3. Настроить сертификат с SAN, доверие CA и доступ консолей только из административной сети.
  4. Выдать отдельные идентичности администраторам. Не раздавать один общий супер-токен.
  5. Создать профили чтения AD и подключения к ПК, проверить их с сервера.
  6. Начать с read-only скана и пилотного пакета. Массовое развёртывание — после сетевых испытаний.
Закрытие консоли не останавливает службу.

Это требование к новому Orkestr. Старые локальные режимы могли зависеть от открытого UI; переносить такое поведение в общую серверную версию нельзя.

Подключение компьютеров из Active Directory

В будущем приложении: «Подключить ПК → Active Directory». В макете видна только учебная форма.

  1. Укажите DNS-имя домена или контроллера, например dc01.lab.test. Это учебный домен.
  2. Выберите профиль чтения AD. Он не обязан иметь права администратора на ПК.
  3. Задайте OU/DN, например OU=Workstations,DC=lab,DC=test, вложенные OU, исключения и импорт disabled accounts.
  4. Запустите серверный preview. Он должен показать найденные объекты, дубликаты, добавления и обновления без записи в inventory.
  5. Подтвердите импорт. Отсутствующие в результате поиска ПК по умолчанию не удаляются.
  6. Отдельно назначьте профиль сканирования/установки и проверьте подключение к пилотному ПК.

Если домен не находится

Проверьте DNS сервера, связь с DC/VPN, часы Windows, доверие домена и права service identity. Успешный запрос AD с ноутбука администратора ещё не доказывает доступ со службы сервера.

В старом Inventory есть ADSI без RSAT и постраничный поиск. В старом Deploy импорт требует ActiveDirectory PowerShell module. В Orkestr предлагается единый ADSI-адаптер, но отдельные AD credentials ещё предстоит реализовать.

Компьютеры вне домена

Без домена доступ не появляется автоматически. Для V1 нужен доступный из сервера компьютер с правильно настроенным WinRM HTTPS и выделенной локальной учётной записью.

  1. Обеспечьте DNS-разрешение имени ПК и сетевой маршрут LAN/VPN с Orkestr-сервера.
  2. На ПК подготовьте сертификат Server Authentication с точным DNS SAN. У сервера Orkestr должна быть доверенная CA-цепочка.
  3. Администратор ПК явно настраивает WinRM HTTPS и узкие правила firewall. Автоматического обхода TLS и UAC не будет.
  4. Создайте уникальную локальную запись с необходимыми правами, не один общий пароль на весь парк.
  5. В окне «Учётные данные» задайте профиль вида TEST-WG-01\emp, ограничьте его конкретными целями.
  6. В «Подключить ПК → Вручную» выберите «Вне домена · WinRM HTTPS» и назначьте профиль.
  7. Проверьте read-only scan с сервера и только затем тестовую установку.
Не «чинить» подключение отключением защиты.

Не использовать TrustedHosts=*, SkipCACheck/SkipCNCheck, Basic по HTTP или AllowUnencrypted. Запрет NTLM политикой не обходится приложением. Настройки UAC должны согласовываться отдельно; их ослабление влияет на всех локальных администраторов.

IP вместо DNS допустим только при соответствующем IP SAN. За пределами доступной LAN/VPN без агента ПК не обслуживается.

Учётные данные и DPAPI

Окно профиля отдельно от окна импорта. В нём задаются назначение, имя пользователя, разрешённые цели и новый пароль. Сохранённый пароль никогда не возвращается в поле редактирования и не показывается клиентам.

Что сохраняет сервер

DPAPI CurrentUser ciphertext под постоянной учётной записью службы. В заданиях находятся только ID профиля и выбранный scope. Папка данных и backup защищаются ACL. Передача с консоли — только по проверяемому HTTPS.

«Зашифрован» не означает «невозможно потерять».

DPAPI защищает хранение. Не защищает от администратора ОС, захвата процесса службы и утраты профиля. Такой переносимый vault вы не запрашивали; усложнять V1 ключами восстановления не планируется.

При ошибке расшифровки нельзя незаметно запускать работу от более привилегированной service identity. Требуется блокировка и действие администратора.

Инвентаризация и коллекции

Карточка ПК объединяет оборудование, ОС, установленное ПО, результат последнего скана и историю заданий. Ошибка одного провайдера не стирает предыдущие сведения и не превращается в успешный пустой список.

Состояния сведений

  • Скан завершён: основные выбранные провайдеры вернули результаты.
  • Частичный скан: часть провайдеров недоступна, причины видны отдельно.
  • Нет актуального скана: соответствие версии неизвестно. Это не «ПО отсутствует».
  • Нет связи: не удалось подтвердить доступность нужного транспорта. Не делать вывод только по ping.

Коллекции

Статическая — выбранные ПК. Динамическая — правило по данным, например ОС, OU, площадке или версии ПО. Перед запуском задания цели материализуются: новая машина, позже вошедшая в коллекцию, не должна незаметно попасть в уже одобренную волну.

Для ПО используется uninstall registry или утверждённое detection rule. Win32_Product не используется из-за побочных эффектов MSI repair. Сбор пользовательских приложений — отдельное ограничение, не решённое старым machine-wide сканером.

Как устроить библиотеку приложений

Приложение — не только EXE и название. Для управляемого обновления нужно связать источник версии, конкретный файл, правила доверия, шаги установки и обнаружение на ПК.

  1. Описание: название, издатель, канал stable/beta, x64/x86/ARM при поддержке.
  2. Источник версии: API, HTML, текст или ручное значение.
  3. Установщик: URL-шаблон либо ссылка, извлечённая со страницы.
  4. Доверие: ожидаемый издатель Authenticode, доверенный hash или явно одобренный внутренний пакет.
  5. Пакет: silent args, acceptable exit codes, зависимости, preflight и reboot policy.
  6. Detection: product code/registry, publisher, версия и архитектура; после установки перепроверить.
  7. Автоматика: check, download, approval/pilot и deploy отдельно.

Скачивание идёт один раз в серверный cache по hash, затем файл передаётся ПК. Плавающая ссылка latest не может менять содержимое уже одобренной revision.

Старые winget-рецепты требуют отдельного решения.

Если каждый ПК сам запускает winget install latest, общий внешний трафик и конкретная версия не закреплены. Для управляемого канала нужна серверная загрузка и immutable artifact. Direct winget допустим лишь как отдельный явно обозначенный режим.

Проверка версии: API, HTML и Regex

JSON API — предпочтительный путь

Укажите HTTPS URL и JSON Pointer. Например для ответа ниже Pointer /version выберет строку 2.4.1.

{
  "version": "2.4.1",
  "channel": "stable"
}

Это учебный ответ, не актуальная версия реального ПО. Если путь отсутствует, значение не строка или формат неизвестен, источник считается неисправным и автоустановка блокируется.

HTML — выбор элемента

Задайте CSS selector, например .release-version. Затем выберите текст или атрибут. Для download link используйте селектор ссылки и href. В V1 предполагается ввод селектора и preview, не полнофункциональный встроенный браузер.

<span class="release-version">Version 2.4.1</span>
<a class="release-download" href="/files/atlas-2.4.1-x64.msi">Download</a>

Ноль или несколько совпадений требуют решения администратора. Страница разбирается без выполнения скриптов. Для JavaScript-only страницы нужен API или ручной источник.

Regex — выделить номер и отфильтровать файл

Версия из текста: (\d+\.\d+(?:\.\d+)?), группа 1. В backend предлагается Rust regex с ограничениями, а не произвольный eval и не .NET regex со сложным backtracking.

Фильтр имени установщика: /atlas-(?P<version>\d+\.\d+\.\d+)-x64\.msi$. Версия из имени обязана совпасть с найденной версией релиза.

Шаблон ссылки

https://downloads.example.test/atlas/{version}/atlas-{version}-x64.msi

При версии 2.4.1 переменная заменяется проверенным значением. Схема и host не должны изменяться через подстановку. Относительные href разрешаются относительно страницы, каждый redirect проверяется заново.

Что показывает тест источника

  • Исходное значение и нормализованную версию.
  • Количество совпадений и причину выбора.
  • Конечный URL, arch/channel, ожидаемый тип файла.
  • Время проверки и безопасный fragment ответа.
  • Ошибку TLS/HTTP/selector/regex без выдачи токена в сообщении.

В текущем HTML проверяется только локальный пример. Настоящие HTTP status, подпись, SHA-256 и redirect здесь не проверяются.

Одобрение, автоскачивание и автополитика

По умолчанию: развёртывание только с одобрением. Новая найденная версия не разрешает запускать installer. Проверка, загрузка и установка — разные действия.

РазрешениеЧто позволяетЧего не позволяет
АвтопроверкаПериодически получить номер новой версии.Скачать или установить без других разрешений.
АвтоскачиваниеЗагрузить candidate в серверный карантин.Считать файл доверенным или одобренным.
Ручное одобрениеРазрешить конкретную revision/hash после проверок.Автоматически менять цели и перезагружать пользователей.
АвтополитикаРазвернуть после заданных проверок, пилота и окна.Обходить ошибки источника/подписи, scopes и network quotas.

Безопасная последовательность

  1. Найти новую версию.
  2. Скачать в quarantine, проверить размер/hash/подпись и издателя.
  3. Закрепить package revision и artifact hash.
  4. Одобрить либо пройти явно включённую unattended policy.
  5. Пилот → наблюдение → оценка ошибок → основная волна.
  6. Detection после установки, reboot только по отдельной политике.

Изменение источника, файла, install script, silent args или detection сбрасывает соответствующее одобрение. Тот же номер версии с другим hash — новый candidate.

Очередь без перегрузки сети

В первой версии речь о заданиях на ПК, не об агентах. Сервер решает, кому и когда передать пакет, сколько установок можно выполнять одновременно и когда повторять ошибку.

Что настраивается отдельно

  • Число Internet-downloads в repository сервера.
  • Передачи на ПК глобально и на каждую площадку.
  • Число установок; на одном ПК — один изменяющий процесс.
  • Случайный разброс старта, окно, интервалы и TTL повторов.
  • Пилот/волны и остановка при превышении порога ошибок.

Черновая стартовая конфигурация: 1 внешняя загрузка, 2 передачи глобально, 1 на площадку, 2 установки, разброс до 120 секунд. Это предложения, не измеренные ограничения вашей сети.

Если нужно совсем по одному

В полной версии — строгий последовательный режим без перекрытия работ по целям. Одних двух полей concurrency=1 недостаточно, если передача следующему ПК идёт одновременно с установкой предыдущего: запрет overlap должен быть частью политики.

Чего пока нельзя обещать

Старый Copy-Item через WinRM не обеспечивает точный лимит Мбит/с. Сначала надёжно ограничиваем число передач; byte-rate появляется только с новым контролируемым адаптером и измерениями. Jitter не заменяет общий scheduler.

Отмена и обрыв связи

Installer, уже запущенный на ПК, может продолжать работу после обрыва или отмены. Система должна показать «нужна сверка», проверить detection/receipt и не запускать всё ещё раз вслепую.

Резервная копия и восстановление

Копия SQLite должна быть согласованной: штатный SQLite backup/VACUUM INTO, а не перенос одного живого файла без WAL. Вместе сохраняются конфигурация, artifact manifest, сертификаты и защищённые секреты по политике.

  1. Проверить, что backup создан с нужными правами и не лежит в общедоступной папке.
  2. Для восстановления остановить выдачу новых заданий, сверить running, остановить службу.
  3. Восстановить согласованный набор данных, не смешивать новую базу со старыми WAL-файлами.
  4. Запустить startup self-check DPAPI/TLS/storage и прочитать состояние очереди.
  5. Проверить read-only доступ с реальной service identity, затем разрешить работу.
Backup данных не гарантирует перенос паролей.

На другом сервере или под другой identity секреты потребуется ввести заново. Даже на том же сервере нужны сохранные Windows profile/DPAPI keys. Это ограничение надо испытать до production.

Возврат старой базы не откатывает уже установленное ПО. Downgrade/uninstall — отдельная vendor-supported процедура.

Частые вопросы

Это будет одно приложение или две программы под одним ярлыком?

Один продукт с общей службой, реестром ПК, библиотекой, очередью, профилями и audit. Две вкладки — только вариант навигации, не две базы.

Почему без агента, если в запросе были агенты?

После уточнения выбран V1 без постоянных агентов. Старые программы тоже работают через remote APIs. Агент — возможный следующий этап с отдельной службой и безопасным enrollment.

Можно одновременно доменные и недоменные ПК?

Да, это требование. Но каждому нужен поддерживаемый транспорт и корректные credentials; само присутствие в inventory не означает доступ для установки.

Почему regex не может просто найти ссылку на любом сайте?

Разные сайты используют JS, API, авторизацию, несколько файлов и разные каналы. Нужны явные extraction rules, preview, ограничения и проверка соответствия версии/архитектуры. HTML сначала разбирается DOM-parser, а не одним regex.

Можно ли автоматически скачивать, но не устанавливать?

Да. Это независимые разрешения. Файл сначала в карантине; approval/deploy отдельно. По умолчанию rollout требует одобрения.

Тёмная тема меняет всё приложение для всех?

Нет. Предпочтение личное на консоли, системная тема следует ОС. В макетах хранится только это значение.

Как перенести старые данные?

Через read-only dry-run импорт копий JSON/SQLite в новую базу с UUID mapping. Расписания и автоустановка после переноса отключены; пароли ввести заново под identity Orkestr.

Группы компьютеров и подгруппы

В макете A откройте «Группы». Название «коллекции» заменено более понятным: умные — по условиям, ручные — по выбранным ПК. Папки организуют вложенность: Приложения → Chrome → Последняя версия / Старая версия.

  1. Раскройте папку и выберите группу. Видны количество ПК, состав, RAM, установленная версия, эталон и состояние ПО.
  2. «Изменить» открывает правила И/ИЛИ и живой предпросмотр. Можно выбрать приложение, сравнение с библиотекой, RAM, ОС или источник ПК.
  3. В папке выберите «Создать подгруппу». Тип «Папка» позволяет сделать ещё один уровень, а поле «Расположение» — перенести существующую группу.
  4. Папка объединяет участников потомков без повторов. Правила детей не наследуются неявно. Циклы и удаление папки с детьми блокируются.
  5. В блоке «Проверить связь с библиотекой» измените учебную версию на 131.0.0.0: умные группы пересчитаются, ручная сохранит состав.

Все версии Chrome учебные, не актуальные релизы Google. Reload сбрасывает группы. Подробная карточка будущего приложения сохраняет разделы исходного Inventory — сокращение HTML не отменяет оборудование, ПО, службы, процессы и остальные сведения. Спецификация групп.
