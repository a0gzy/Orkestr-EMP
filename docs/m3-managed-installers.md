# M3.6 — управляемые MSI и EXE на сервере

Состояние на 26 ноября 2026: реализация серверного этапа, реальный сетевой пилот
установок ещё не принят. Сервер использует одну очередь для MSI и EXE. Дизайн и
выбор веб-интерфейса отложены до M5.5; сервер и API от этого выбора не зависят.

## Подготовка файла

На сервере под его identity, после настройки защищённого каталога данных:

```powershell
target\debug\orkestr-server.exe stage-msi --data C:\OrkestrData --file C:\Packages\example.msi
target\debug\orkestr-server.exe stage-exe --data C:\OrkestrData --file C:\Packages\example.exe
```

Это примеры путей, а не указание устанавливать эти пакеты. Команды только помещают
локальный файл в `artifacts/<sha256>.msi` или `.exe` и возвращают SHA-256.
UNC, относительные пути, неверное расширение, reparse-файлы и файлы свыше 256 MiB
не принимаются. Проверяются MSI/PE-заголовки; DLL и текст под видом EXE отклоняются.
Это структурная проверка, не гарантия исправности, подписи или доверенного издателя.
Authenticode и политика библиотеки остаются M4. Исходный файл не запускается.

## Ревизия через HTTPS API

Admin отправляет `POST /v1/deploy/revisions` с JSON:

```json
{
  "name": "Example (учебный пример)",
  "version": "1.2.3",
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "product_code": "11111111-1111-1111-1111-111111111111",
  "execution": { "kind": "Exe", "arguments": "/S /norestart" }
}
```

Хеш, GUID, версия и параметры выше учебные. Используйте фактический hash staging,
GUID системной записи приложения и точное значение `DisplayVersion` из
`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{GUID}` в 32/64-bit view.
EXE без такой GUID-записи в этом этапе не поддержан. Пользовательские установки,
произвольные registry paths, file/version detection и автоматическое определение
тихих параметров ещё не реализованы.

`arguments` — явная непустая командная строка производителя, до 2048 UTF-8 байт,
без управляющих символов. Кавычки задаёт автор согласно формату установщика.
Она передаётся напрямую в `ProcessStartInfo.Arguments`, без `cmd`, eval и интерполяции
PowerShell. Секреты в аргументы не помещать: ревизии доступны администраторам.
Сам сервер не умеет доказывать, что EXE действительно соблюдает quiet/no-restart:
автор проверяет параметры производителя на отдельной тестовой ВМ.

Для MSI поле `execution` можно опустить либо передать `{ "kind": "Msi" }`.
Произвольные параметры MSI в этом этапе не принимаются; сохраняются фиксированные
`/qn /norestart REBOOT=ReallySuppress ALLUSERS=1`.
Неизвестные поля и типы исполнения отклоняются. Изменение типа, параметров, hash,
GUID или версии создаёт отдельную неизменяемую ревизию, не меняя старые планы.

## План, одобрение и результат

1. `POST /v1/deployments` с `Idempotency-Key` и
   `device_id/package_revision_id/connection_id/connection_revision` создаёт
   `WaitingApproval`. Файл и параметры закреплены в плане.
2. Admin отдельно отправляет `POST /v1/deployments/{id}/approve` с
   `{ "expected_revision": 1 }` для новой записи. Viewer и Operator не могут
   регистрировать, планировать или одобрять установки.
3. Перед запуском сервер повторно проверяет полномочия, ревизии профилей, identity,
   соответствие цели и SHA-256 локального файла. На цели создаётся защищённый
   временный каталог, файл передаётся через WinRM HTTPS и хеш проверяется повторно.
4. Проверка версии до запуска исключает повтор, если версия уже присутствует.
   Иная версия той же GUID-записи блокирует установку; автоматический upgrade поверх
   неё в этом этапе не разрешён.
5. После завершения 0 + подтверждённая версия дают `Succeeded`, 3010 + версия —
   `RebootRequired`. Сервер сам не перезагружает ПК. Другие vendor-specific success
   codes пока не настраиваются. Код 0 без версии не считается успехом.

Вывод EXE и stderr считываются параллельно и отбрасываются, не накапливаясь в памяти,
SQLite или API. Для диагностики сохраняются код выхода, detection и история попыток.
Отсоединённый дочерний installer, timeout, обрыв или restart могут оставить исход
неизвестным: `NeedsReconciliation` удерживает блокировку ПК. Действие `reconcile`
только читает версию, без повторного копирования или запуска. Повтор возможен
только после доказанного отказа до запуска, с новым одобрением, максимум три попытки.

В текущей консоли EXE регистрируется через API, после чего пакет доступен для создания
плана. В карточке плана перед одобрением показаны ревизия, hash, GUID, версия и EXE
arguments. Форма регистрации в консоли пока только для MSI. Это ограничение текущего
интерфейса; серверный механизм EXE завершён в рамках описанного контракта.

## Обновление базы

SQLite v8 запрещает старым серверам открывать новые данные. Перед миграцией v7
создаётся согласованный `*.before-v8-<uuid>.sqlite`; backup не перезаписывается.
У старых MSI без поля execution сохраняется прежняя семантика. Обновляйте сервер и
консоль совместно; старый клиент может отвергать EXE-данные. Возврат к v7 требует
восстановления всей согласованной копии, а не ручного понижения `user_version`.

```powershell
.\tools\check-core.ps1 -Gnu -CompilerBin (Join-Path $env:LOCALAPPDATA 'OrkestrEMP/toolchains/w64devkit/bin')
```

Форматирование, Clippy `--workspace --all-targets --locked -- -D warnings`,
**113 тестов** и сборка workspace прошли. Полный локальный лог —
`test-results/m3.6-core-check.log`. Отдельно прошли проверка ссылок изменённых Markdown,
разбор синтаксиса PowerShell и smoke справки серверного EXE с новой командой staging.

Добавлены проверки формата PE, параметров, прежнего MSI JSON, Admin/RBAC,
неизменяемых ревизий, общего одобрения и блокировки после restart для MSI/EXE,
миграции v7 → v8 с backup. В Windows-тесте транспорт и detection подменены;
настоящий блок запуска выполняет локальный тестовый EXE, который проверяет
кавычки/спецсимволы, пишет большой stdout/stderr и возвращает 3010. Он ничего
не устанавливает. Это не доменная приёмка и не проверка сторонних установщиков.

В разрешённом пилоте нужно отдельно проверить реальный quiet/no-restart EXE,
работу через сохранённые credentials, WinRM/потерю связи, detection, 3010 и рабочую
группу. Произвольные Command/PowerShell/File Copy, многошаговые пакеты, reboot,
logoff, message и nested packages остаются незавершённой частью M3.
