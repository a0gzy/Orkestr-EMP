# Два направления интерфейса

## A. Боковая навигация — выбрана владельцем

Структура Workbench, прохладный Cobalt: узкая постоянная панель, рабочая область
ПК/библиотеки/очереди и контекстная карточка. Основные разделы — не названия старых программ,
а объекты и действия единого продукта.

Плюсы: легко добавить политики/аудит/настройки, не потерять раздел при работе,
перейти из карточки ПК к библиотеке и заданиям. Вкладки внутри карточки:
обзор / ПО / задания; внутри приложения: пакет / источник / политика.
Минус: панель занимает ширину; можно свернуть, таблица не должна иметь десятки колонок.

Владелец подтвердил A и сохранение текущего геометрического знака Orkestr.
Пробел исправлен: в A есть раздел «Группы компьютеров», дерево `Приложения → Chrome →
Последняя / Старая версия`, папки внутри папок, умные/ручные группы, создание,
изменение, перенос, И/ИЛИ, RAM, software conditions, счётчики и preview состава/ПО.
Смена учебного эталона библиотеки пересчитывает группы. Это HTML/JS, не сервер.
Подробности — [collections.md](collections.md). Сокращённая карточка макета не заменяет
полную карточку исходного Inventory и не означает отказ от других функций.

## B. Верхние рабочие разделы — альтернатива

Структура Split Studio, тёплая Coral: два заметных верхних раздела
«Инвентаризация» и «Развёртывание». В первом — ПК/коллекции; во втором — библиотека,
очередь и политики. В библиотеке — список слева, редактор выбранного приложения справа.

Плюсы: знакомый переход от двух программ, больше ширины для таблиц.
Минусы: функции могут снова восприниматься как два продукта; нужна сквозная карточка
ПК, общий поиск и общие профили. Нельзя делать вторую базу или второе окно сервера.

Макеты действительно отличаются расположением навигации, начальным экраном,
контекстом и компоновкой; это не просто две палитры одного скриншота.

## Общие правила

- «Подключить ПК» — отдельный workflow: AD / вручную / CSV, preview, test, import.
- «Учётные данные» — отдельное окно с объяснением identity сервера, scope и DPAPI.
  В HTML это modal `<dialog>`; в egui возможно самостоятельное native viewport.
  Уточнить, нужны ли плавающие OS-окна или достаточно дочерних окон внутри консоли.
- Просмотр ПК не раскрывает секрет. Secret edit не заполняется сохранённым паролем.
- Изменения библиотеки не запускают установку. Одобрение и планирование разделены.
- Тема личная: Light/Dark/System, контрастные semantic tokens, не invert-фильтр.
- Русский основной; terminal/code/версии моноширинные, UI — читаемый sans.
- Для offline HTML — локальные системные шрифты Segoe UI / Consolas через токены.
  Будущая Rust-сборка должна встроить лицензированный кириллический font, не полагаться
  на наличие web font или стандартный egui fallback для всех языков.
- Клавиатурный фокус, Escape, подписи полей, понятные ошибки, статусы не только цветом.
- Без фальшивого графика SLA, production-счётчиков, выдуманных текущих vendor versions.

## Границы макета

Нет fetch запросов, DPAPI и auth. Fixtures вымышлены и обозначены.
Работают локальное редактирование/preview, HTML text/attribute extraction,
URL-шаблон и href + regex-проверка версии; browser storage содержит только выбор темы.
После reload данные и «одобрения» исчезают. Поле пароля учебное, не сохраняется и не логируется.
HTML-проверка regex предназначена для демонстрации UX и не заменяет Rust validator.
Отображаемые jobs/квоты — расчётный preview, не наблюдение реальной сети.

Текущие токены в `../tokens.css` предварительные; макет A уже выбран, далее уточняются
плотность, размеры и соответствие egui theme с сохранением знака Orkestr. Веб-макет не означает
переход приложения на Electron/Tauri или добавление web-runtime в V1.
