# Orkestr EMP

Сервер инвентаризации и управляемого развёртывания ПО для Windows-сетей.

Перенос разработки: [получение исходников, сборка и новый dev-сервер](docs/development.md).
В Git нет `target`, компиляторов, старых приложений, test-data и секретов.

**Приоритет с 26 ноября 2026:** довести сервер по roadmap, затем пересмотреть дизайн
и работу интерфейса с API. В M5.5 добавлена оценка веб-интерфейса без отдельного
Rust-клиента, с установкой только сервера. Текущая egui-консоль используется для
проверки серверных сценариев; окончательный интерфейс ещё не выбран.

**Статус: серверные функции M3–M5 реализованы через HTTPS API, SQLite v10.**
Добавлены все штатные шаги Deploy с checkpoints, настраиваемая библиотека/загрузчик,
коллекции по known/approved versions, политики pilot/soak, квоты, окна и сохранённые
повторы. [Контракт и команды](docs/m3-m5-server.md),
[фактическая приёмка и ограничения](docs/m3-m5-verification.md).
На SERVER01 проверены synthetic EXE 0/3010, пропуск установленного пакета, библиотека/
политика без открытого клиента и workflow со сбором Inventory. На SERVER01/PC01
прошли параллельные и последовательные передачи с проверкой квот/скорости. У Ассистента прошли
источник, загрузка и подпись; рецепт тихой установки отклонён после неудачного пилота.
Workgroup, конкурентная полевая нагрузка и SCM/reboot lifecycle ещё не приняты.
Исходные Open Deploy и Open Inventory не изменены и не скопированы целиком.

В `crates/` — общий реестр SQLite, immutable scans/package revisions,
движок/редактор ручных и умных групп, импорт выбранных копий с dry-run и rollback.
Локальный режим M1 сохранён; server mode — отдельный процесс, не готовая замена старых приложений.
Запуск: [нативная консоль M1](docs/m1-console.md), границы: [m1-core.md](docs/m1-core.md).

## M2: один сервер, несколько консолей

[Команды и ограничения M2](docs/m2-server.md), [фактические проверки](docs/m2-verification.md).
`target\debug\orkestr-server.exe` — init/run/service; в консоли появилась кнопка
**«Подключиться к серверу…»** и отдельные окна credentials, connections, operators/audit.
Персональные отзываемые tokens, Admin/Operator/Viewer, expected revisions, bounded
read-only jobs, защищённый локальный NTFS и server-side DPAPI. По умолчанию — loopback.
С доменного ПК проверена доступность LDAPS и WinRM HTTPS на согласованных целях.
Проверки через сохранённые профили Orkestr и SCM остаются открытыми.
Ни domain join, ни отключение TLS для локальной разработки не нужны.

## M3.1: offline-ядро инвентаризации (основа)

[Контракт и CLI-команды](docs/m3-inventory-core.md), [проверки и Not run](docs/m3-inventory-verification.md).
Ручной/CSV preview с явным apply/backup, 23 typed F21 provider reports, нормализация
ПО со scope/version evidence, Partial/Unknown без ложного пустого успеха. SQLite v4
с pre-upgrade backup; действующие функции M1/M2 сохранены. Новых окон/API/AD/CIM
адаптеров и сетевых сканов в этом инкременте нет; deploy engine не реализован.

## M3.2: окно добавления ПК и статусы

[Инструкция и API](docs/m3-console-api.md), [проверки/Not run](docs/m3-console-api-verification.md).
**Компьютеры → Добавить компьютеры…**: ручной список/локальный UTF-8 CSV → preview
старых/новых name/site → подтверждение → backup/apply. Local и HTTPS mode; remote write
только Admin, путь файла серверу не передаётся. В карточке — последняя попытка и вкладка
**Провайдеры**, безопасная и для Viewer. SQLite v5 хранит receipt успешного apply;
повтор того же ID не дублирует запись. Реального AD/CIM Inventory и Deploy пока нет.

## M3.3 — профили WinRM HTTPS

**Настройки → Подключения к ПК / AD…**. Для профиля компьютера можно выбрать
Negotiate для домена или рабочей группы либо Kerberos для домена. Сервер проверяет
сохранённое подключение чтением названия ОС через CIM. [Настройка и обновление](docs/m2-server.md).

## M3.4–M3.5 — сетевой Inventory и MSI

В серверном режиме Admin может просмотреть компьютеры из OU перед добавлением,
запросить скан из карточки ПК и одобрить установку зарегистрированного MSI в разделе
«Пакеты». Старт установки, сверка версии и история попыток сохраняются в SQLite v7.
[Порядок пилота](docs/testing.md#ручной-пилот-m3).

## M3.6 — EXE через серверный API

Добавлены `stage-exe` и тип EXE в существующем API ревизий. Тихие параметры задаются
явно, сохраняются в ревизии и показываются перед одобрением; EXE запускается напрямую.
Проверка результата — системная GUID-запись и точная версия. Очередь, блокировка ПК,
отмена до запуска и сверка после обрыва общие с MSI. SQLite v8.
[Контракт и ограничения](docs/m3-managed-installers.md).

## Запустить локальную консоль

После сборки: **`target\debug\orkestr-console.exe`**. Без аргументов — выбор существующей
базы / создание пустой, без учебных данных по умолчанию. В одной консоли — ПК,
группы, сохранённые подробности Inventory, пакеты, импорт и read-only review
выключенной legacy-автоматики. Никаких установок/сканов.

Сборка/тесты: `tools/check-core.ps1` (для GNU: `-Gnu -CompilerBin <свой-GCC-bin>`).
Пилоты M3–M5 используют отдельные защищённые данные в игнорируемом `test-results/`.

## Посмотреть

Откройте **[index.html](index.html)** двойным щелчком, без сборки и Интернета.

- [Макет A — боковая навигация](mockups/sidebar.html): **выбран владельцем**.
- [Макет B — верхние разделы](mockups/tabs.html): оставлен для сравнения, не основной.
- [Офлайн-справочник](docs/index.html): описание будущих сценариев и ограничений.

В макетах работают переходы, поиск, выбор ПК/приложения, окна подключения и учётных
данных, редактор источника версии, проверка на локальных примерах, модель одобрения,
предпросмотр очереди, светлая/тёмная/системная тема. Только тема сохраняется в браузере.
В A также работают группы и подгруппы: папки, умные/ручные выборки, редактор условий,
preview состава/ПО, перенос по дереву и пересчёт от учебной версии библиотеки.
Данные синтетические; никаких подключений к ПК, скачиваний или установок не происходит.
**Не вводите настоящие пароли в макет.**

## Согласовано с владельцем

| Вопрос | Решение |
|---|---|
| Интерфейс | Современный спокойный, без визуального шума |
| Выбранная концепция | Макет A — исходное направление; дизайн пересмотреть в M5.5, знак Orkestr сохранить |
| Аудитория и масштаб | Open source для небольших/средних организаций; стартовая сеть владельца около 50 ПК |
| Группы компьютеров | Ручные/умные, вложенные папки и подгруппы, редактор, количество/список ПК и ПО |
| Примеры коллекций | Chrome =/< последней известной версии в библиотеке; RAM >=16, >=8, <8 и 8–<16 ГБ |
| Топология | Один сервер Windows; сейчас консоль, веб-доступ и установка только сервера рассматриваются в M5.5 |
| Первая версия | Без постоянных агентов; WinRM/CIM |
| Обновления | Развёртывание с одобрением по умолчанию; можно включить автополитику |
| Учётные данные | Сохранение на этом сервере, DPAPI под идентичностью службы |
| Перенос паролей | Не требуется; при смене машины/идентичности — повторный ввод |
| Подключение ПК | Отдельное окно: AD, ручной ввод, импорт |
| Ввод учётных данных | Отдельное окно; ссылки на секреты вместо паролей в заданиях |

Автоскачивание независимо от автоустановки. Предлагаемый безопасный старт:
проверять по расписанию, загружать проверенные кандидаты в карантин на сервер,
устанавливать только после одобрения. Включение автоскачивания при первом запуске
требует явного выбора администратора. Точные лимиты и расписания ещё не согласованы.

## Что объединяем

- `../pdqdeployconsole/app`: Rust + egui, пакеты и шаги, WinRM, расписания,
  JSON, служба и центральная SMB-очередь.
- `../pdqinventoryconsole-2/app`: Rust + egui, AD, CIM, коллекции, SQLite,
  HTTPS API, служба, DPAPI для недоменных ПК.

Фундамент: Rust-сервер, общая серверная служба и SQLite,
перенести Deploy на единый HTTPS API, выделить устойчивую очередь и библиотеку ПО.
Это не склейка двух окон и не переименование старых EXE.
Выбор итогового интерфейса выполняется после серверных этапов.

## Сейчас не сделано

Нет release-дистрибутива `OrkestrEMP.exe`, реальной криптографии/аутентификации в HTML,
агентов, сетевых интеграционных испытаний, измеренной пропускной способности,
полной инструкции с проверенными командами установки Orkestr.
Для групп есть локальные Rust-engine, SQLite и нативный редактор; серверное
совместное использование доступно в dev-контуре M2. Сокращение карточки ПК в макете не отменяет подробные разделы Inventory
и не означает удаления остальных функций.
Справочник помечает проектируемые операции и не выдаёт их за существующие.

## Проверка материалов

Из этой папки, при установленном Python и Node.js:

```powershell
py -3 tools/validate.py
node --check mockups/app.js
node --check mockups/groups.js
node --check docs/help.js
```

Это проверки материалов, не тесты Rust-приложения. Rust-проверки: `tools/check-core.ps1`.
Фактический результат текущей проверки — [docs/verification.md](docs/verification.md).
Названия, лицензии и уведомления зависимостей исходных проектов нужно сохранить
при переносе кода. Проприетарные бинарные файлы и материалы исследования не включать
в дистрибутив Orkestr.
